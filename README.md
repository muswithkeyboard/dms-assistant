# Ассистент ДМС (прототип хакатона)

Веб-сервис для менеджера сопровождения ДМС. Отвечает только по документам выбранного договора или группы компаний
(ГК), у каждого вывода — ссылка «документ → пункт → фрагмент», проверенная кодом. Разбирает отказы клиник (SC 01:
«можно / нельзя / при условиях / недостаточно данных»), отвечает об условиях, программах и клиниках, ведёт
добавление клиники через HR и СК (SC 02). Работает без модели и без ключей (режим `guided`, ADR 0009). Письма —
только черновики: сервер ничего не отправляет.

## Что нужно заранее

- Docker Desktop с `docker compose` **или** Python 3.12+ (`pyproject.toml`: `requires-python = ">=3.12"`) и
  [uv](https://docs.astral.sh/uv/).
- Комплект организаторов (в git его нет, ADR 0007): папка `Кейсы_обезличенные/Документы/ГК N/Компания M/…`.
- Необязательно: энкодер rubert-tiny2 в ONNX (`data/models/rubert-tiny2-onnx/`, 28 МБ) — для маршрутизации вопросов
  kNN. Нет папки — сценарий выбирают только правила (`index/embed.py:get_encoder` возвращает `None`).
- Необязательно: ключ модели (раздел «Модель»). Без ключа сервис работает полностью в режиме `guided`.
- Браузер Google Chrome (интерфейс проверялся на 1366×768 и 1920×1080).

## Где лежат данные

Код находит данные через `DMS_DATA_DIR` (по умолчанию `app/data` — ссылка на `../data`):

```text
Hackathon2/
  app/                                                     ← этот репозиторий
  data/raw/Кейсы_обезличенные/Документы/ГК 1/Компания 1/…  ← комплект (только чтение)
  data/models/rubert-tiny2-onnx/                           ← энкодер (необязательно)
  data/derived/                                            ← разбор, индекс, файлы клиентов (создаётся сервисом)
  data/app/                                                ← чаты, запросы, черновики, разметки, профили СК (SQLite)
```

В чистом клоне создайте ссылку на папку данных:

```bash
cd app
ln -s ../data data
```

## Запуск в Docker (основной путь)

```bash
cd app
docker compose up --build
```

Откройте http://127.0.0.1:8080. Порт публикуется только на 127.0.0.1 (`DMS_PUBLISH` в `docker-compose.yml`).
Комплект монтируется только для чтения из `../data/raw` (или `DMS_RAW_DIR`), энкодер — из `../data/models`
(или `DMS_MODELS_DIR`). Лимит памяти контейнера по умолчанию 2 ГБ (`DMS_MEM_LIMIT`) — нижняя граница целевого
сервера (ADR 0009). База разбора в Docker пустая (том `dms-derived`): выполните импорт (ниже).

## Запуск без Docker

```bash
cd app
uv sync --extra dev
uv run python scripts/ingest_kit.py      # разбор комплекта → data/derived/kit.sqlite
uv run dms serve                         # http://127.0.0.1:8080
```

Адрес сайта. Сервис отвечает только на имена `127.0.0.1`, `localhost` и `[::1]` (заголовок Host; иначе 403 —
защита от DNS-rebinding). Если ассистент открывается по имени сервера или через обратный прокси, перечислите имена
в `DMS_ALLOWED_HOSTS` через запятую без порта, например `DMS_ALLOWED_HOSTS=dms.example.ru,10.0.0.5` (в `.env`
или окружении; в Docker — в `.env`). Изменяющие запросы `/api/*` со стороннего сайта (Origin не совпадает с
адресом, `Sec-Fetch-Site: cross-site`) отклоняются 403, тело JSON принимается только с `Content-Type:
application/json` (415).

Память и скорость. При старте сервис в фоне строит поисковые индексы договоров (`DMS_WARM=0` — при первом вопросе).
В памяти держится до `DMS_CLAUSE_CACHE_MAX` пунктов (по умолчанию 200 000, ~0,5 ГБ; весь комплект — ~61 тыс.). Для
группы из 100 договоров на сервере с запасом памяти — `DMS_CLAUSE_CACHE_MAX=1000000` (~1 ГБ, ответ 2–4 с вместо ~20).

## Импорт комплекта

Страница «Документы» → вкладка «Документы» → «Импортировать комплект», дождаться «Импорт завершён». То же из
командной строки: `uv run python scripts/ingest_kit.py`. Импорт заново собирает базу из `data/raw/` и затем заново
разбирает договоры подключённых клиентов (ADR 0011 п. 5). Импорт — самый тяжёлый по памяти момент (пик 613 МБ в
Docker, ADR 0009); на сервере 2 ГБ его лучше выполнять до начала работы.

## Подключение клиента (ADR 0011)

Страница «Документы» → вкладка «Подключение клиента»:

1. «Новый клиент» → название группы компаний, юрлица (СК — выбрать или «Определить по документам», номер —
   необязательно) → «Создать клиента». По каждому юрлицу — свой договор.
2. Загрузить файлы договора (docx, xlsx, pdf, txt; формат проверяется по содержимому). Документы, общие для всех
   договоров, — в блок «Общие документы группы».
3. «Обработать» — фоновое задание: определение СК → разбор → проверка полноты → договор в базе → самопроверка. Ход —
   статусы ТЗ п. 7.1, итог — отчёт о готовности: `ready` (есть пункты, программы, перечень клиник и матрица видов
   помощи), `limited` (договор в поиске, но без перечня или матрицы), `failed` (пункты не разобраны).
4. «Открыть чат по договору» — чат доступен при `ready` и `limited`, перезапуск сервиса не нужен.

Файлы клиентов хранятся в `data/derived/clients/` (вне git).

## Разметка таблиц для неизвестной СК (ADR 0012)

Если СК не распознана (договор `limited`), в карточке договора на вкладке «Подключение клиента» — «Разметить
таблицы»: выбрать таблицу с клиниками, отметить строку заголовка (или «строки заголовка нет»), роли колонок (название
клиники обязательно; адрес, город, вид помощи, программа, франшиза и др.), откуда программа. «Пробный разбор»
показывает результат без сохранения; «Применить ко всем таблицам с такой же раскладкой» — для перечней «по таблице на
программу»; флажок профиля СК сохраняет разметку для следующих договоров той же СК. Затем «Сохранить разметку» и
«Обработать». Таблица, похожая на таблицу премий, требует подтверждения (`mapping_suspicious`).

Флажок «Не распознавать формат (разобрать как неизвестную СК)» разбирает договор известной СК запасным разборщиком —
так проверялась разметка на настоящих договорах.

Матрица «программа × вид помощи» (ADR 0013) размечается тем же экраном: таблица «Это матрица видов помощи» (строки —
виды помощи, колонки — программы; или длинная таблица программа / вид помощи / входит) либо флажок у перечня «Виды
помощи из этого перечня → матрица». «Нельзя» по матрице — только явное «нет»; суммы и лимиты в ячейках не учитываются
(видны в пробном разборе). С перечнем и матрицей договор неизвестной СК — `ready`.

## Модель (необязательно)

Режим движка — `DMS_ENGINE_MODE=auto|guided|agent` (по умолчанию `auto`; `guided.py:engine_mode`): без модели или с
«малой» моделью (`DMS_LLM_SMALL=1`) — `guided`, с сильной моделью — `agent`. Провайдер — в `.env` (`.env.example`,
ADR 0002):

| `DMS_LLM_PROVIDER` | Что ещё задать |
|---|---|
| пусто | без модели — `guided` |
| `anthropic` | `ANTHROPIC_API_KEY`, `DMS_LLM_MODEL` |
| `openai_compat` | `DMS_LLM_MODEL`, `OPENAI_API_KEY` и/или `DMS_LLM_BASE_URL` (OpenAI, YandexGPT, vLLM, Ollama `/v1`) |
| `gigachat` | `GIGACHAT_CREDENTIALS` |

В `guided` модель используется только по флагам: `DMS_GUIDED_LLM_SUMMARY=1` — формулировка краткого вывода по уже
проверенным утверждениям, `DMS_GUIDED_LLM_SLOTS=1` — дополнение слотов (по замеру ADR 0009 малые модели выдумывают
слоты, поэтому по умолчанию выключено). Живые модели с ключами не проверялись — ключей нет.

Модель-помощник (ADR 0015): если модель задана, она переписывает непонятый правилами вопрос своими словами в
стандартный вид («к лору сходить, это бесплатно?» → «Входит ли приём оториноларинголога в программу?»); ответ по
документам строит код, в ответе видно «Понял вопрос как …». Проверено на локальной qwen3:1.7b через Ollama без
ключей: `ollama pull qwen3:1.7b`, в `.env` — `DMS_LLM_PROVIDER=openai_compat`, `DMS_LLM_MODEL=qwen3:1.7b`,
`DMS_LLM_BASE_URL=http://127.0.0.1:11434/v1` (из Docker — `http://host.docker.internal:11434/v1`),
`DMS_LLM_REASONING=none`, `DMS_LLM_SMALL=1`. `DMS_LLM_ASSIST=0` — выключить помощника.

## Проверка

```bash
cd app
uv run pytest -q
uv run bash scripts/verify.sh      # тесты, конфиги, гигиена git, опись комплекта, сервер и заголовки
docker compose run --rm verify     # то же в образе
```

Тесты без комплекта и без живой модели ставят SKIP.

## Ограничения (коротко)

- Неизвестная СК: без разметки — только поиск по пунктам договора; после разметки перечня и матрицы — клиники, выбор
  клиники и метки. Строки неразмеченных таблиц без программы при нескольких программах договора дают «при условиях»,
  а не «можно» (защита от условий чужой программы).
- Модели нет: ответ строит код (`guided`); свободные вопросы вне шаблонов дают «нужно уточнение» или найденные пункты.
  Метка SC 01 консервативна: при сомнении — «недостаточно данных», а не догадка.
- «Можно» и «нет в перечне» по клинике — только после выбора клиники менеджером из перечня (ADR 0010).
- Письма не отправляются: «Скопировать», «Скачать .txt», «Открыть в почте» (`mailto:` по клику).
- Нет входа и ролей; публичной ссылки нет. Подробно — `docs/limitations.md`.
