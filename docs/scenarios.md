# Поддержанные сценарии

ТЗ п. 5 и п. 10.3. Как сценарии ведёт режим **`guided`** (ADR 0009) — режим по умолчанию: без модели и без ключа
ответ строит код. Он сам вызывает инструменты договора, ссылается ровно на то, что они вернули, затем идёт общий путь
`citations.verify` → `decide_label` (`config/verdict_rules.yaml`) → `compose`. Модель необязательна: с флагами
`DMS_GUIDED_LLM_SLOTS=1` и `DMS_GUIDED_LLM_SUMMARY=1` (по умолчанию выключены) она только дополняет слоты (через `grounded()` — слово должно стоять в вопросе) и формулирует
краткий вывод по уже проверенным утверждениям. Режим `agent` (сильная модель сама вызывает инструменты) остаётся для
сравнения; ниже он не описывается. Ветки и тексты меняются в `config/`, не в коде (`docs/rules.md` п. 5). Устройство —
`docs/architecture.md`, ограничения — `docs/limitations.md`, сценарий показа — `docs/demo_script.md`.

## Общие правила

| Правило | Как работает | Где |
|---|---|---|
| Чат = один контекст | группа компаний целиком или договор (юрлицо); фиксируется при создании; программа и дата расчёта — необязательно | `dms_api/service.py` `_validate_context`, ТЗ п. 9 |
| Только документы контекста | инструменты привязаны к одному договору; условия другого договора не переносятся | ADR 0005, `tools/registry.py` |
| Каждый вывод — со ссылкой | «документ → пункт, строка таблицы или строка перечня → фрагмент»; цитата должна дословно найтись в этом пункте этого договора, иначе утверждение не показывается | `citations.py`, ADR 0003 |
| Метку ставит код | по таблице правил, первое сработавшее правило; модель метку не ставит | `config/verdict_rules.yaml`, `engine.py` |
| Клинику подтверждает менеджер | код предлагает кандидатов из перечня, «можно» и «нет в перечне» — только после клика | ADR 0010 |
| Каталог и правила СК — не договор | «ЛПУ_Регионы» и правила страхования не используются как условия договора | `config/precedence.yaml` `not_contract_terms`, `config/doc_types.yaml` |
| Инструкции в документах — данные | текст «игнорируй правила» внутри пункта не меняет поведение: guided текст пунктов только цитирует, агент получает его как данные | `guided.py`, `config/prompts/agent_system.md` п. 3 |
| Письма не отправляются | только черновики: «Скопировать», «Скачать .txt», «Открыть в почте» по клику | `docs/rules.md` п. 3 |

## Маршрутизация

Сценарий выбирает `guided.choose_scenario` → `scenarios/route.py`, модель не вызывается:

1. **Правила по словам** (`config/route_markers.yaml`). Явный отказ («отказали», «не приняли») и вопрос о покрытии
   («входит ли», «положено ли») — всегда SC 01, это ничто не перебивает.
2. **kNN по эмбеддингам** (rubert-tiny2 в ONNX, примеры — свои формулировки `config/route_examples.yaml`, не
   эталоны) — побеждает правила, только если уверен (отрыв ≥ `min_margin` = 0,5). Нет энкодера — решают правила.
   Точность выбора сценария на 57 вопросах: правила 0,68, kNN 0,75, вместе 0,81 (ADR 0009).
3. **Слоты** — из текста вопроса и перечня договора: услуга, вид помощи (`config/care_types.yaml`), клиника (номер
   и второе слово названия, строчные названия по отличительным словам перечня), улица, город, программа, договор
   (в чате по ГК — только если однозначно указывает на один договор).

| Сценарий | Код | Подпись в интерфейсе |
|---|---|---|
| Разбор отказа / «положено ли» | `sc01` | Разбор отказа |
| Условия договора, программ, услуг, клиник | `sc02_info` | Условия договора |
| Подбор клиники | `sc02_clinic` | Подбор клиники |
| Добавление клиники | `sc02_add_clinic` | Добавление клиники |

## Уточнения (FR 14)

Обязательные факты — `config/required_facts.yaml`. `blocking: true` — без факта вывода нет, вместо ответа вопрос
(статус «Нужно уточнение»). `blocking: false` — ответ даётся, недостающее — в «Нужно уточнить». Факты копятся по
запросу: ответ менеджера на вопрос дополняет слоты (`service.py` `answer_message`).

| Сценарий | Блокирует | Не блокирует (ответ есть, вопрос в «Нужно уточнить») |
|---|---|---|
| SC 01 | услуга, если клиника не названа; программа, если у договора их больше одной | услуга при названной клинике («без неё проверена только клиника»); клиника при отказе; договор в чате по ГК |
| Подбор клиники | вид помощи; программа (если их больше одной) | город или район |
| Добавление клиники | клиника; программа (если их больше одной) | вид обращения — но без него автомат стоит в «Недостаточно данных» |

## SC 01. Разбор отказа клиники

Вопрос вида «клиника отказала в услуге — обоснованно?», «положено ли …», «входит ли …».

### Проверки guided (`guided._sc01`)

| Проверка | Как | Значения |
|---|---|---|
| `care_in_program` — вид помощи в программе | строка матрицы «программа × вид помощи» (`care_matrix`); из совпавших строк — подходящая по способу оказания (очно / на дому / телемедицина / стационар) и классу услуги; узкая строка «в объёме …» не подтверждает услугу другого класса (`config/service_classes.yaml`, этап w12-care); затем пункты «входит» программы | `yes` · `absent` (строка матрицы `present=false`) · `not_found` |
| `exclusion` — исключение | поиск по исключениям программы и договора по лемме слова услуги («диспансеризация» ≠ «диспансерное наблюдение») | `yes` · `absent` · `not_found` |
| `conditions` — условия | франшиза, направление, согласование, зона, лимит, «по направлению» строки перечня; отказ клиники без проверенной причины — условие «уточните причину» | список |
| `documents` — противоречие | пункты разного содержания об одном (`config/precedence.yaml`) | `contradictory` |
| `clinic_in_program` — клиника в перечне программы | только по строке, выбранной менеджером (ниже) | `yes` · `absent` · `not_found` |
| `clinic_confirmed` | выбор менеджера учтён (`clinic_choice.selected`) | `yes` · `no` |

Недоказанная проверка (нет живой ссылки) становится `not_found` (`citations.py` `_fix_checks`). «Можно» требует ещё,
чтобы услуга была названа в тексте «входит» или сама была строкой матрицы, исключения были просмотрены и в обращении
не было отказа клиники (`guided.allowed_blocker`); иначе `care_in_program` понижается до `not_found`.

### Метки (`config/verdict_rules.yaml`, сверху вниз, первое сработавшее)

| Правило | Когда | Метка | Что значит для менеджера |
|---|---|---|---|
| `excluded` | исключение найдено и подтверждено ссылкой | Нельзя | услуга прямо исключена документом |
| `care_absent` | вида помощи нет в матрице программы (`absent`) | Нельзя | матрица разобрана и в ней явное «нет» |
| `clinic_absent` | клиники нет в перечне **и** менеджер нажал «Нет в перечне программы» | Нельзя | клиника не входит в программу; к ответу — альтернативы и кнопка добавления |
| `contradiction` | документы противоречат друг другу | При условиях (нужно подтверждение СК) | показаны оба фрагмента; позиция — по старшему документу |
| `clinic_unresolved` | услуга входит, клиника названа, но не подтверждена (не нашли / «нет в перечне» без выбора / выбрана строка другого вида помощи) | Недостаточно данных («выберите клинику из перечня») | нужен клик в карточке «Уточните клинику» |
| `conditions` | услуга входит, есть условие | При условиях | условие — отдельным утверждением со ссылкой |
| `covered` | услуга входит, клиника в перечне, условий нет **и** строку выбрал менеджер | Можно | каждый шаг доказан ссылкой |
| `unknown` | всё остальное, в том числе любой `not_found` и «нет проверенных ссылок» | Недостаточно данных | в «Нужно уточнить» — что не найдено и что спросить |

Пометка `denied_with_alternative` — «Нельзя (есть альтернатива)», если подбор нашёл клинику той же программы.
Правило `covered_by_program` («можно» по программе без клиники) выключено по ревизии w5-coverage (6 ложных «можно»).

**«Не нашли» никогда не даёт «Нельзя»** (`docs/rules.md` п. 3а): `absent` допустим, только если разобран документ
нужного типа (`absent_sources`: для исключений и вида помощи — программа, договор, допсоглашение; для клиники —
перечень, договор, программа) и в ответе перечислено просмотренное.

### Выбор клиники (ADR 0010)

1. Клиника названа → guided собирает до `CLINIC_CHOICE_MAX` (6) кандидатов из перечня программы этого договора (строгие
   совпадения и подходящий вид помощи — первыми) и отдаёт их в `Answer.clinic_choices`. Метка до выбора —
   «Недостаточно данных».
2. Карточка «Уточните клинику»: «В вопросе: «…»», кандидаты (адрес, вид помощи, франшиза или «франшиза не
   применяется», «по направлению», «Источник»), поиск «Найти в перечне: название, улица, город» с «Показать весь
   перечень» / «Показать ещё n», кнопка «Нет в перечне программы».
3. Клик → `POST /api/requests/{id}/clinic`; сервис проверяет, что строка из перечня этой программы этого договора,
   и пересчитывает ответ на тот же вопрос с `clinic_picks`. Строка → проверки по ней; «Нет в перечне» →
   `clinic_in_program = absent` при полученном перечне программы.
4. Выбор относится к последнему ответу; новый вопрос его сбрасывает. В ГК — выбор по каждому договору отдельно.

Почему так: при сопоставлении по тексту ревизия 5 дала 6 ложных «можно» и 3 ложных «нельзя» (похожие названия,
латиница, филиалы). С выбором менеджера — 0 ложных на 7 наборах ревизий (`docs/test_report.md` §3).

## SC 02. Условия договора, программы, услуги и клиники (`guided._sc02`)

| Тип вопроса | Что делает guided | Инструменты |
|---|---|---|
| График взносов, даты | ближайший взнос от даты расчёта чата (или сегодня) и пункты договора об оплате; дату и сумму считает код | `payments_next`, `date_calc`, `search_clauses` |
| Сравнение программ | если в вопросе названы две программы и слова сравнения | `compare_programs` |
| Есть ли клиника в программе | кандидаты и выбор клиники, как в SC 01; ответ — по выбранной строке (вид помощи, франшиза, условие доступа) | `clinics_query` |
| Какие клиники / подбор | перечень программы с нужным видом помощи, затем альтернативы | `clinics_query`, `clinics_pick` |
| Входит ли вид помощи (справочно) | строка матрицы программы с учётом способа и класса услуги | `care_matrix` |
| Остальное | найденные пункты договора дословно, со ссылками | `search_clauses` |

Метки SC 01 справочный ответ не ставит; статус — по ТЗ 8.1 (ниже). Вопрос вне шаблонов даёт найденные пункты или
«Нужно уточнение» — guided не выдумывает связный вывод.

### Подбор альтернативной клиники (ТЗ п. 5.2.2 шаг 1)

Только клиники **той же программы** договора с нужным видом помощи (`scenarios/clinics_pick.py`, допущение A6).
Порядок: без франшизы → размер франшизы не указан → с франшизой; затем рядом с указанным городом или адресом; затем
та же сеть. До 5 клиник. У каждой — основание из полей строки перечня и источник (документ и строка перечня).
Клиника другой программы того же договора доступной не считается.

### Контекст «вся группа компаний» (FR 08)

Guided проходит каждый договор группы отдельно; ответ — блок «По договорам» на договор со своими ссылками. Общий
вывод из разных договоров не складывается; статус ответа — худший из статусов договоров. Если вопрос о сотруднике
и договор не ясен — «Какое юрлицо / договор у застрахованного?» (не блокирует).

## Добавление клиники в программу (ТЗ п. 5.2.2, ADR 0004)

Запускает только менеджер: кнопка «Запустить: альтернатива и добавление клиники» под ответом (движок предлагает её,
если в вопросе названа клиника или сценарий — о клиниках) или «Добавить клинику» в инструментах запроса. Переходы —
`config/add_clinic.yaml`, письма — `config/texts_ru/drafts.yaml`, код — `scenarios/add_clinic.py`.

Начальное состояние определяет код: нужны договор, программа, клиника и **вид обращения** — без любого из них
`insufficient`. Затем клиника ищется в перечне **этой программы с этим видом помощи**.

| Состояние (полоса автомата) | Что делает система | Черновик | Кнопки |
|---|---|---|---|
| Альтернатива в программе (`alt_found`) | клиника есть в перечне программы — показать её и альтернативы | не нужен | «Завершить» |
| Клиники нет в программе (`not_in_program`) | альтернативы той же программы; если клиника есть в другой программе договора — «не считается доступной» | HR: клиники нет, альтернативы, можно запросить добавление | «HR хочет добавить клинику» |
| HR хочет добавить (`hr_wants_add`) | сформировать запрос в СК | письмо в СК о добавлении | «Письмо в СК готово — ждём ответа» |
| Ждём ответа СК (`awaiting_insurer`) | менеджер вставляет ответ СК (сохраняется как источник) и выбирает ветку | — | «СК ответила: бесплатно» / «СК ответила: платно» |
| По ответу СК: бесплатно (`insurer_free`) | клиника отмечена добавленной в запросе | HR «клиника добавлена» | «Завершить» |
| По ответу СК: платно (`insurer_paid`) | запросить согласие HR | HR: условия из ответа СК | «HR согласовал условия» / «HR отказался» |
| HR согласовал — ждём подтверждения СК (`hr_agreed`) | клиника ещё не добавлена | письмо в СК с подтверждением согласия | «СК подтвердила добавление» |
| СК подтвердила добавление (`insurer_confirmed`) | клиника отмечена добавленной в запросе | HR «клиника добавлена» | «Завершить» |
| HR отказался (`hr_declined`) | запрос завершается | — | «Завершить» |
| Недостаточно данных (`insufficient`) | не хватает договора, программы, клиники или вида обращения — уточнить вопросом в чате | не формируется | «Завершить» |

Правила автомата:

- ветку «бесплатно / платно» выбирает менеджер по ответу СК; система её не угадывает;
- клиника «добавлена» только после ответа СК и только в запросе — документы договора не меняются;
- повтор шага и повторный запуск с той же клиникой ничего не дублируют и ничего не отправляют;
- в письме — тема, обращение, юрлицо и договор, программа, клиника, вид обращения, суть; неизвестное поле —
  «[ЗАПОЛНИТЬ]»; сведения о застрахованном добавляет менеджер;
- обещаний нет: сроки, «гарантия», «будет добавлена», «согласовано» ловит `config/forbidden_promises.yaml`. Такое
  в ответе СК — поле письма очищается, ответ СК остаётся источником; правка черновика с обещанием не сохраняется.

## Статус ответа (ТЗ п. 8.1)

Ставит `compose.py` по каждому договору, затем худший по ответу, в порядке приоритета:

| Статус | Когда |
|---|---|
| Источники противоречат друг другу | противоречие документов; показаны оба фрагмента |
| Нужно уточнение | есть уточняющие вопросы (не хватает блокирующего факта) |
| Данных недостаточно | нет ни одного утверждения с проверенной ссылкой, или метка SC 01 «Недостаточно данных» |
| Есть подтверждение в документах | всё остальное: выводы опираются на проверенные ссылки |

Процентов уверенности нет. Метка (SC 01) и статус — разные вещи: «Нельзя» со статусом «Есть подтверждение» значит
«отказ обоснован, и вот документ».

## «Нет в документах» и «не нашли» (FR 23)

| | «Нет в документах» (`absent`) | «Не нашли» (`not_found`) |
|---|---|---|
| Когда | документ нужного типа загружен и разобран, и строка матрицы `present=false`, или менеджер выбрал «Нет в перечне программы» при непустом перечне | всё остальное: документа нет, поиск ничего не вернул, проверка не доказана ссылкой |
| В ответе | что просмотрено и ссылка на документ | «Недостаточно данных» и вопрос |
| Может дать «Нельзя» | да | никогда |

## Договор подключённого клиента (ADR 0011–0013)

Сценарии те же; от готовности договора зависит, какие проверки доступны:

| Готовность | Что есть | Что получает SC 01 |
|---|---|---|
| «Готов» (`ready`) | пункты, программы, перечень клиник, матрица видов помощи (разборщик СК или разметка оператора) | все проверки и метки, как у комплекта |
| «Готов с ограничениями» (`limited`) | пункты; нет перечня или матрицы | без перечня — нет выбора клиники; без матрицы — нет `care_in_program`: метка «Недостаточно данных», ответ найденными пунктами. Ложных «можно» / «нельзя» не добавляется |
| «Ошибка» (`failed`) | нет разобранных пунктов | чат недоступен |

Неизвестная СК → оператор размечает перечень клиник и матрицу «программа × вид помощи» на экране «Разметить таблицы»;
профиль СК размечает следующие договоры той же СК. «Нельзя» по размеченной матрице — только при явном «нет» в ячейке.

## Чаты и запросы (ТЗ п. 9, FR 10–12)

- Новый чат не наследует историю соседнего; для другого контекста — новый чат.
- Запрос создаётся с первым вопросом; внутри — сообщения, выбор клиники, автомат, черновики. «Закрыть запрос»,
  «Открыть снова», оценка 1–5 с комментарием.
- По умолчанию видны открытые запросы, закрытые — по «Показать закрытые».
- Всё хранится в `data/app/app.sqlite` и открывается после обновления страницы и перезапуска.

## Документы оператора (ТЗ п. 7, FR 01–03)

Страница «Документы», вкладка «Документы»: дерево ГК → договоры → документы, кто и когда загрузил, источник, формат,
статус ТЗ п. 7.1, предупреждения, пункты документа, «Не предоставлены» в карточке договора. «Импортировать комплект»
разбирает все договоры комплекта. Новый клиент — вкладка «Подключение клиента» (загрузка → обработка → отчёт).
