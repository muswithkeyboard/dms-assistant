# ADR 0009. Режим «guided»: ответ ведёт код, модель необязательна — для сервера 2–4 ГБ

Принято 24.10.2026 по требованию пользователя: прототип должен работать на очень маленьком веб-сервере
(«нано/пико», 2–4 ГБ оперативной памяти, без видеокарты), без платных ключей.

## Контекст
- Агент из волны 2 (модель сама вызывает инструменты, ≤ 8 шагов) требует модель с надёжным вызовом инструментов.
  qwen3:8b (~5 ГБ) в 2–4 ГБ не помещается; модели 0,6–1,7B помещаются, но вызывают инструменты ненадёжно и на 1–2
  ядрах CPU медленны. Дообучение на таком железе невозможно и по плану §1 п. 1 не делается.
- Замер на M1 (qwen3:8b): режим «размышлений» — 26–37 с на простой ход; без него (`reasoning_effort: none`) —
  0,7–4 с при той же скорости генерации (~10 ток/с). Длина вывода решает больше, чем размер модели.
- Нужные для ответа данные уже структурированы (волна 1): матрица «программа × вид помощи», перечни клиник,
  пункты с номерами, график взносов; метки и ветки — в конфиге (ADR 0002: логика в коде).

## Решение
1. Новый режим `guided` (`src/dms_core/guided.py`): по сценарию и слотам код сам вызывает инструменты договора
   (care_matrix, clinics_query, clinics_pick, search_clauses по исключениям/условиям, payments_next, date_calc),
   собирает DraftAnswer со ссылками ровно на то, что вернули инструменты, и дальше идёт обычный путь
   citations.verify → decide_label → compose. Модель не нужна.
2. Модель — необязательный помощник: (а) извлечение слотов, когда правила не справились (1 короткий вызов);
   (б) формулировка краткого вывода по уже проверенным утверждениям (1 короткий вызов, проверка summary в compose).
   Без модели — шаблонные формулировки из config/texts_ru/ui.yaml.
3. Выбор режима — `DMS_ENGINE_MODE=agent|guided|auto` (auto: guided, если модели нет или она «малая» —
   DMS_LLM_SMALL=1; agent — для сильной модели). extractive остаётся запасным.
4. Локальная модель для слабого сервера — Ollama с `DMS_LLM_REASONING=none`; кандидаты 0,6–1,7B выбираются
   сравнением (план §10.2) после согласия пользователя на загрузку.

## Последствия
- Ответы на типовые вопросы SC 01/SC 02 воспроизводимы и не зависят от модели; агентный режим остаётся для сильной
  модели и сравнения. Свободные вопросы вне шаблонов в guided дают «нужно уточнение» или найденные пункты.
- Метрики §10.1 считаются для обоих режимов; в отчёте о тестах — отдельно guided и agent.

## Практики, на которые опирается решение (обзор 24.10.2026)
| Практика | Как у нас |
|---|---|
| Сначала детерминированный конвейер, модель — только узкие задачи (извлечение, формулировка) | guided: инструменты вызывает код; модель — слоты и краткий вывод |
| Маленькая модель в квантовании GGUF Q4 через llama.cpp/Ollama, без «размышлений» | Ollama, `DMS_LLM_REASONING=none`; кандидаты Qwen3-0.6B/1.7B, Gemma 3 1B — выбор сравнением на своих кейсах |
| Строгий вывод по схеме (constrained decoding), схемы маленькие и плоские, одна повторная попытка | guided-вызовы без инструментов, `json_schema` маленькая; ретрай — llm/_common |
| Схема гарантирует синтаксис, но не правду: проверять значения по исходному тексту | слоты — `grounded()` по тексту вопроса; цитаты — `citations.verify` по тексту пункта |
| Проверка на уровне утверждений (claim-level grounding): каждое утверждение — свой фрагмент | `supports`, связь утверждения с цитатой (`citations.related`), summary только по живым утверждениям |
| Отказ/«данных недостаточно» вместо догадки, калибровка отказов | `not_found` ≠ «нельзя»; метка без живых ссылок → insufficient |
| Оценка на размеченном наборе с отложенной частью, а не «JSON валиден» | eval: К10–К19 + свои кейсы, holdout (ADR 0008), метрики по договорам |
| Стабильный короткий системный промпт (кеш префикса), малый контекст и ограничение длины ответа ради памяти | короткие промпты guided, `max_tokens` 120–200; `num_ctx` Ollama — в README для сервера |

Оценка памяти сервера: сервис ≤ 500 МБ (цель этапа w5-guided) + Qwen3-1.7B Q4 ≈ 1,1–1,4 ГБ весов + KV-кеш при
контексте 2–4 тыс. токенов — порядка 2–2,5 ГБ; в 4 ГБ помещается, в 2 ГБ — только без модели (guided) или с 0,6B.

## Замер 24.10.2026 (scripts/bench/, вопросы К10–К19 + свои кейсы без holdout, 57 вопросов)
Разбор вопроса: сценарий из четырёх и слоты (клиника, программа, город…), ответ строго по JSON-схеме,
без «размышлений», 2 потока, контекст 2048. Mac M1 (ядра быстрее типичного vCPU VPS — на сервере медленнее).

| Способ | Сценарий верно | Слоты «не из вопроса» (выдумка) | Задержка | Память |
|---|---|---|---|---|
| Правила `route.rule_scenario` | 0,68 | — (только из текста) | < 1 мс | — |
| kNN по эмбеддингам rubert-tiny2 (1 сосед) | 0,74 | — | 3,5 мс (1 поток) | +~150 МБ (torch; пик процесса 402 МБ) |
| qwen3:0.6b (GPU M1 / CPU 10 вопр.) | 0,72 / 0,7 | 30 из 57 вопросов | CPU p50 2,7 с, p95 5,9 с; ~35 ток/с | ~0,8 ГБ при контексте 2048 |
| qwen3:1.7b (GPU M1 / CPU 10 вопр.) | 0,56 / 0,6 | 10 из 57 | CPU p50 9,6 с, p95 21,6 с; ~9 ток/с | ~1,6 ГБ при контексте 2048 |

Выводы: маленькие модели не лучше правил и kNN в выборе сценария и выдумывают слоты (у 0.6b — в половине
вопросов), а на CPU медленнее на 3–4 порядка. По умолчанию для сервера 2–4 ГБ — guided без модели; маршрутизация —
правила + kNN по эмбеддингам (энкодер ~150 МБ; для сервера лучше ONNX-версия без torch — новая зависимость,
нужно согласие пользователя, `docs/rules.md` п. 15). Модель — только по флагу и только для формулировки краткого
вывода (слоты от модели принимаются лишь через grounded()). Выборка мала (57 вопросов) — числа ориентир.

## Энкодер в продукте (24.10.2026, решение пользователя: onnxruntime + tokenizers)
rubert-tiny2 выгружен в ONNX и квантован int8 (`scripts/export_encoder.py`, вне git: data/models/rubert-tiny2-onnx/,
28 МБ; fp32 — 111 МБ). Векторы int8 к исходной torch-модели: косинус 0,94–0,96; на маршрутизации int8 = fp32.
Маршрутизация (`scenarios/knn_route.py`, примеры — свои формулировки в `config/route_examples.yaml`, не эталоны):
kNN побеждает правила, только если уверен (отрыв ≥ min_margin = 0,5), иначе решают правила.
Точность выбора сценария на 57 вопросах эталонов (без holdout): правила 0,68; kNN 0,75; сочетание 0,81.
Порог выбран на этих же вопросах — подтверждается на holdout при финальном замере. kNN — 1,1 мс на вопрос.
Память и время всего сервиса (uvicorn, ответы по ГК 3 — 5 договоров, режим без модели):
| Где | Без энкодера | С энкодером |
|---|---|---|
| macOS, RSS после двух ответов | 107 МБ | 231 МБ (первый ответ 1,0 с — загрузка модели, далее 0,16 с) |
| Docker (Linux, mem_limit 2 ГБ), после ответа, без импорта | — | 150 МБ |
| Docker, сразу после импорта комплекта в том же процессе | — | 613 МБ (пик разбора) |
Вывод: сервис с энкодером помещается в 2 ГБ с большим запасом; импорт комплекта — самый тяжёлый момент
(~0,6 ГБ), на сервере 2 ГБ его лучше делать заранее или перезапускать сервис после импорта.
Docker проверен впервые: найдено и исправлено падение на старте из-за прав 600 у файлов статики
(Dockerfile: chmod a+rX); `docker compose run --rm verify` — PASS 8, FAIL 0.
